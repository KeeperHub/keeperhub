## Surfaces & Scope

The contract below covers **6 surfaces**, in render order on `/hub`:

1. **Page hero** — `Hub` headline + sub copy (replaces the Phase-43 `HubHero` headline + sub).
2. **Tab strip + search bar band** — three pill tabs + search input, sticky-ish below the hero.
3. **Protocols tab content** — responsive grid of `ProtocolCardV2`.
4. **Workflows tab content** — Phase 43 view-shell body lifted into `_workflows-tab.tsx`. Protocols strip + "Templates" header/divider removed.
5. **Marketplace tab content** — popularity-sorted leaderboard table with sort dropdown.
6. **Page-shell glue** — fixed sidebar (existing nav-sidebar — single "Hub" entry, no secondary Marketplace link), page chrome around the tabs.

### 1. `HubTabsShell` (`app/hub/_tabs-shell.tsx` — NEW client component)

**Owns:** the `<Tabs value={activeTab} onValueChange={...}>` wiring + the tab-strip band + the URL ↔ value sync.

```tsx
// Skeleton shape (planner refines during execution)
"use client";
import { useRouter, useSearchParams } from "next/navigation";
import { useTransition } from "react";
import { Tabs, TabsList, TabsTrigger, TabsContent } from "@/components/ui/tabs";

const TABS = ["protocols", "workflows", "marketplace"] as const;
type TabValue = (typeof TABS)[number];

export function HubTabsShell({
  initialTab,
  protocolsContent,
  workflowsContent,
  marketplaceContent,
}: {
  initialTab: TabValue;
  protocolsContent: React.ReactNode;
  workflowsContent: React.ReactNode;
  marketplaceContent: React.ReactNode;
}): React.ReactElement {
  const router = useRouter();
  const searchParams = useSearchParams();
  const [isPending, startTransition] = useTransition();

  const handleChange = (value: string) => {
    if (!TABS.includes(value as TabValue)) return;
    const params = new URLSearchParams(searchParams.toString());
    params.set("tab", value);
    startTransition(() => {
      router.replace(`/hub?${params.toString()}`, { scroll: false });
    });
  };

  return (
    <Tabs value={initialTab} onValueChange={handleChange} className="w-full">
      <div className="flex items-center justify-between gap-4 border-b border-border/20 py-2 mb-6">
        <TabsList className="inline-flex items-center gap-1 bg-transparent p-0 h-auto">
          {/* Pills — see Tab pill spec below */}
        </TabsList>
        <HubTabSearch activeTab={initialTab} />
      </div>
      <TabsContent value="protocols">{protocolsContent}</TabsContent>
      <TabsContent value="workflows">{workflowsContent}</TabsContent>
      <TabsContent value="marketplace">{marketplaceContent}</TabsContent>
    </Tabs>
  );
}
```

**Why a client component:** Radix Tabs needs client state for the value-binding; the URL `router.replace` call is client-only. Server components for the actual tab CONTENT trees are passed in as props (RSC-in-CC pattern), so SSR streaming still happens for Protocols and Marketplace.

```tsx
// Skeleton — planner refines during execution
import { unstable_cache } from "next/cache";
import { db } from "@/lib/db";
import { workflows, workflowPayments } from "@/lib/db/schema-*";
import { sql, desc, eq } from "drizzle-orm";
import { MarketplaceRow } from "@/components/hub/marketplace-row";
import { MarketplaceSortDropdown } from "@/components/hub/marketplace-sort-dropdown";

const fetchLeaderboard = unstable_cache(
  async (sort: "popular" | "newest" | "top-calls", cursor: string | null) => {
    // Whitelist columns explicitly per MARKET-04.
    return db
      .select({
        listedSlug: workflows.listedSlug,
        displayName: workflows.name, // verify exact column during execution
        publicTags: ..., // join + agg
        callCount: sql<number>`count(${workflowPayments.id})`.as("call_count"),
        priceUsdcPerCall: workflows.priceUsdcPerCall,
        chain: workflows.chain, // or wherever Base/Tempo lives
        listedAt: workflows.listedAt,
      })
      .from(workflows)
      .leftJoin(workflowPayments, eq(workflows.id, workflowPayments.workflowId))
      .where(eq(workflows.isListed, true))
      .groupBy(workflows.id)
      .orderBy(...)
      .limit(50);
  },
  ["marketplace-leaderboard"],
  { revalidate: 60, tags: ["marketplace"] }
);

export async function HubMarketplaceTab({ searchParams }): Promise<React.ReactElement> {
  const sort = searchParams.sort ?? "popular";
  const cursor = searchParams.cursor ?? null;
  const rows = await fetchLeaderboard(sort, cursor);

  if (rows.length === 0) {
    return <MarketplaceEmptyState sort={sort} />;
  }

  return (
    <>
      <div className="flex items-center justify-between mb-4">
        <p className="text-xs text-muted-foreground" aria-live="polite">
          Showing 1–{rows.length} of {/* total — separate count query or estimate */}
        </p>
        <MarketplaceSortDropdown active={sort} />
      </div>
      <div role="table" aria-label="Marketplace leaderboard" className="rounded-xl overflow-hidden border border-border/20 bg-[var(--color-hub-card)]">
        <MarketplaceLadderHeader />
        {rows.map((row, idx) => (
          <MarketplaceRow key={row.listedSlug} row={row} rank={idx + 1} />
        ))}
      </div>
      {/* pagination button if more results */}
    </>
  );
}
```

## Open Issues for the planner to resolve during /gsd-plan-phase 44

These are NOT design decisions; they are implementation forks the planner picks up. Limited to the 3 most consequential per orchestrator instruction.

1. **ProtocolCardV2 workflow count source.** Two paths:
   - (a) Extend `/api/protocols` to return `workflowCount` per protocol (count of public workflow templates whose `nodes` reference each protocol). Server-cached. Adds API surface but keeps the card contract clean.
   - (b) Compute client-side by intersecting `protocols` and the existing `getPublic()` workflow list. No API change but couples the Protocols tab data dependency to the Workflows tab fetch — defeats the goal of independent tabs.
   
   **Recommendation:** (a). Add the count to the API. If the heuristic for "this workflow uses this protocol" is unreliable (e.g., nodes only carry an action-slug, not a protocol-slug), fall back to rendering `View workflows →` instead of `{N} workflows`. Lock the chosen approach in the SUMMARY.

2. **Sort dropdown UI options vs. API options.** MARKET-02 + MARKET-07 require the API to expose `popular | recent | top-calls` (`recent` = `newest`). But `Top calls` is functionally identical to `Popular` today (both order by `count(workflow_payments)` desc). Showing both in the UI confuses humans.
   - **Recommendation:** UI exposes `Popular` and `Newest` ONLY (two options). The API exposes all three for agent compatibility. Document the divergence in the SUMMARY. If product wants three UI options, the planner may swap in `Top calls` and remove `Popular` (they're aliases).

3. **Tab strip search bar — defer cross-tab wiring or ship full per-tab search.** ROADMAP success #1 says "search bar visible alongside the tab strip". CONTEXT.md gives the planner discretion on whether the search input wires across tabs or is per-tab.
   - This UI-SPEC ships the search input visually + wires it per-active-tab (Workflows uses the existing Phase-43 search, Protocols filters client-side, Marketplace filters via `?q=`). Cross-tab UNIFIED search (single input that simultaneously searches all three surfaces and shows results from all three in a unified results panel) is **deferred** — it requires a results-panel design and a server-side multi-source search endpoint that does not exist today.
   - **Recommendation:** ship as spec'd above (per-active-tab search). Mark the cross-tab unified search as a future sub-phase (already listed in CONTEXT.md `Deferred Ideas`). If the planner discovers that even the per-tab Protocols/Marketplace search is overscope, defer Marketplace `?q=` to post-Phase-44 and ship Protocols + Workflows search only — both filter client-side off already-fetched data, zero new endpoints.
